1At a glance

SOME/IP services can be protected with mutually authenticated DTLS 1.2 by configuration alone: a service sets "unreliable_secure": <port> in the JSON config and application code doesn't change. The crypto lives in the library, behind a backend interface (OpenSSL 3 first), in new classes next to the existing UDP endpoints. Service discovery multicast stays plaintext.

Crypto backend (OpenSSL 3)Built; handshake, mutual auth, data and close_notify pass in the standalone simulation
Per-peer DTLS sessionBuilt; retransmit timer and callbacks exercised by the simulation
DTLS server / client endpointsWritten, never compiled; must be adapted to the 3.7.5 endpoint API
JSON dtls parserWritten; not yet called from configuration_impl
Factory, routing and config wiringNot started: DTLS endpoints are never created at runtime yet
Unit, integration and network testsNot started; only the standalone simulation exists
Cookie exchangeImplemented incorrectly: cookie isn't tied to the client address (see §7)
Build switchENABLE_DTLS, default OFF; all DTLS code behind VSOMEIP_HAS_DTLS

Maturity: experimental. The branch shows the design and the verified crypto core, and asks for early feedback. It is not ready for production or for an upstream pull request.

2Architecture

Five architecture decisions shape the code. DTLS lives in new classes alongside the UDP endpoints, which stay unmodified. OpenSSL is reached only through dtls::backend, so Mbed TLS or an HSM-backed library can replace it. There is one session per remote IP and port, DTLS is opt-in per service, and SD multicast stays plaintext.

4Configuration

{
  "dtls": {
    "enable": "true",
    "version": "1.2",
    "cipher_list": "ECDHE-ECDSA-AES128-GCM-SHA256",
    "certificate": "/etc/vsomeip/ecu.pem",
    "private_key": "/etc/vsomeip/ecu.key",
    "ca_bundle":   "/etc/vsomeip/ca.pem",
    "verify_peer": "true",
    "handshake_timeout_ms": 5000,
    "cookie_exchange": "true"
  },
  "services": [
    { "service": "0x2444", "instance": "0x0001",
      "unreliable_secure": "32444" }
  ]
}
  • Additive only. Existing keys keep their meaning; unreliable still means plaintext UDP.
  • Mutual auth by default. With verify_peer on, a missing ca_bundle disables DTLS instead of silently accepting any peer.
  • Missing certificate or key also disables DTLS.
  • Transition: unreliable and unreliable_secure together are allowed only while peers migrate, and should log a warning.
  • Not yet active: the parser exists but configuration_impl doesn't call it, and handshake_timeout_ms is parsed but not enforced.

5Verification approach

Each left-side level of the V-model has a matching test level. Test specs are written together with the level they verify. Process IDs follow Automotive SPICE 3.1.

What the simulation proves

  • OpenSSL 3 context, ECDSA certificates, CA chain check
  • Full DTLS 1.2 handshake with HelloVerifyRequest
  • Mutual authentication with the pinned cipher
  • Encrypted data both ways; graceful close_notify

What it does not prove

  • That the vsomeip endpoints compile or work
  • Config → factory → endpoint creation; SD → connect → handshake
  • SOME/IP messages and TP over DTLS; loss, many peers, MTU
  • Failure cases, hybrid mode, OFF build identical to upstream

7Known issues from code review

Found by reading the code on 16–17 Sep 2026. None has been fixed yet. The first two block any meaningful community test of the full library.

SeverityIssueLocationConsequence
HighThe cookie is a copy of one process-wide secret, not an HMAC of the client address (the code comment says it is). If RAND_bytes fails, the secret falls back to predictable bytes.dtls_backend_openssl.cpp:33–67Anyone who gets one cookie can use it from any spoofed address, so the cookie exchange gives no DoS or amplification protection.
HighDTLS endpoints don't compile: the server calls asio_socket_factory::create_udp_socket(io_, _error) as a static function, and both endpoints override the pre-3.7.5 tp_segmentation_enabled(service_t, instance_t, method_t).dtls_udp_server_endpoint_impl.cpp:36; *_endpoint_impl.hppENABLE_DTLS=ON fails to build the library.
MediumAny new source address creates a session; there is no limit and no idle eviction.dtls_udp_server_endpoint_impl.cppMemory exhaustion from spoofed traffic.
MediumSession callbacks capture shared_from_this(), creating endpoint → session → callback → endpoint cycles.both endpoint .cpp filesEndpoints and sessions are never freed until stop or restart.
Mediumhandshake_timeout_ms is parsed but never enforced; the link MTU is hard-coded to 1500.dtls_backend_openssl.cpp:200Stalled handshakes hold state; smaller-MTU networks may fragment or fail.
MediumThe server can send only to peers that already completed a handshake.dtls_udp_server_endpoint_impl.cppEvents can't reach subscribers without an established session.
Lowcipher_list uses OpenSSL syntax, and the server session factory isn't given the peer address.dtls_backend.hppBlocks a second backend (Mbed TLS) and a correct cookie design.
LowThe minimum is OpenSSL 3.0, which reached end of life in Sep 2026.CMakeLists.txtRecommend 3.5 LTS as the documented baseline.

8Asking the vsomeip community to review and test

COVESA hosts vsomeip. Its GitHub repository has Discussions and Issues enabled, and the project holds a monthly community call (third Monday of the month, 16:00 CET). COVESA mailing lists and Slack access are requested through the COVESA wiki.

  1. Fix the two High issues first. Reviewers lose interest quickly in code that doesn't build, and a broken cookie design will be the first security comment.
  2. Open a GitHub Discussion, not a pull request. Post an RFC in COVESA/vsomeip Discussions, link test/dtls-udp and both PDFs, and label it experimental.
  3. Ask concrete questions. How clients learn a remote service needs DTLS, fail-closed vs fallback, server-initiated events. Maintainers answer specific design questions faster than "please review".
  4. Give testers a recipe and a report format. The simulation command, the build ON/OFF commands, and: OS, compiler, Boost, OpenSSL version, command, result, logs.
  5. Ask for a slot at the monthly community call to present the design (10 minutes, using this summary).
  6. Split the upstream contribution once feedback is in and tests are green: (1) backend + session + unit tests, (2) endpoints, (3) config and factory wiring, (4) example and docs. Each as a PR against master, following CONTRIBUTING.md (clang-format pre-commit hook).
Draft discussion post
RFC: opt-in DTLS 1.2 over UDP for vsomeip (experimental branch, feedback wanted)

We are prototyping native DTLS 1.2 for unicast SOME/IP over UDP, enabled per service by config ("unreliable_secure": <port>) with no application changes. SD multicast stays plaintext. DTLS lives in new endpoint classes next to the UDP endpoints, with crypto behind a backend interface (OpenSSL 3 first). It is compiled only with -DENABLE_DTLS=ON.

Branch: duonghvu/vsomeip@test/dtls-udp (vsomeip 3.7.5 base). Summary and requirements: documentation/dtls/. Status: crypto core verified in a standalone simulation; library wiring and tests not done.

Questions: (1) Would maintainers accept this direction upstream, and in what PR split? (2) Should the client learn that a remote instance needs DTLS from local config only, or is an SD option acceptable? (3) Fail closed when DTLS is misconfigured, or fall back? (4) Preferred way for the server to reach subscribers before they complete a handshake?

Testers: please run examples/dtls_simulation/run_simulation.sh and report OS, compiler, Boost and OpenSSL versions with the result.
